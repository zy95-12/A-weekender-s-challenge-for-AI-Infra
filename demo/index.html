01

TEE / Confidential Computing

通过硬件隔离与远程证明建立运行时可信边界，结合按证明释放密钥，保护计算中的数据。重点投入 Confidential GPU、可信 I/O 与 CPU—GPU 联合证明，并明确各组件的保护范围。

运行时保护
安全性 ★★★★☆
推理性能负面影响 ★★☆☆☆
依赖硬件可信边界、证明链与实现；仍需评估侧信道。

03

Split-Infer

企业端与云端分担模型层，联合设计切分位置、激活传输、KV 管理与调度，平衡端侧资源、时延和吞吐。中间激活仍可能被反演，需要用真实攻击评估暴露风险。

端云协同
安全性 ★★★☆☆
推理性能负面影响 ★★★☆☆
取决于切分深度与攻击能力；通信和调度决定性能成本。
04

FHE · 全同态加密

由客户端加密输入，云端执行密文计算，再由密钥持有者解密结果。关注矩阵运算加速、非线性近似与密文开销，先评估范围明确的高敏子任务。

密文计算
安全性 ★★★★★
推理性能负面影响 ★★★★★
依赖密码学参数与密钥管理；完整模型密文推理成本高。
05

MPC · 安全多方计算

通过秘密共享等协议，让多方协同计算并限制单方获得完整数据。关注通信轮次、预处理成本和非线性算子协议；安全保障取决于参与方与合谋假设。

多方协作
安全性 ★★★★★
推理性能负面影响 ★★★★☆–★★★★★
依赖协议与合谋假设；跨方通信轮次影响明显。

评级沿用完整洞察报告，为指定威胁模型下的定性比较，不是实测分数或安全认证。安全性星数越多表示保护能力越强；性能负面影响星数越多表示额外成本越大。FHE 为全同态加密的标准缩写。

核心判断：TLS 在服务端终止后，明文仍可能进入运行时。安全方案应回答“防谁、保护什么、性能预算多少”，而不是只看技术标签。

PR #15 原始攻击代码 ↗

安全性优化：增加企业侧部署层数

我们用简单的 MLP，在固定攻击预算下验证了更深的企业侧前层有助于降低 token 恢复率。它说明深度可以增加当前攻击的难度，不构成绝对安全证明。

量化结果与数据分布强相关：同样的深度，在当前 4K 样本和独立公开测试集上的恢复率存在显著差异。表中为 PR #15 的真实归档结果，不随左侧输入变化；不能将某个样本的恢复率推广到所有业务数据。

已有研究通过学习有针对性的噪声分布、扰动中间表示来进一步增强隐私保护，例如 Shredder。这类方法需要同时验证隐私收益与模型精度；本项目尚未实现或测量噪声防护。

若仅对现有激活做轻量加性扰动，不改变模型层数和传输张量规模，预计额外系统负载较小；带训练、去噪等步骤的方案需另行评估。因此，后续系统优化以企业侧保留前 4 层为起点，固定采用 Split · 4 / 27 / 5。这是性能研究的配置选择，不是安全达标结论；当前实测未启用噪声。

05 真实系统优化

        
开环负载下，比较 SLO 与吞吐。

        

          
C16 Baseline：通信、流水与调度是优化重点

          

            通信开销与云侧处理同量级，需要优化通信路径。
            SplitInfer 引入了显著的端云通信开销，往返 RPC
            耗时与云侧处理时间相当， 远高于仅按“通信量 /
            带宽”估算的时间。差额包含固定链路时延，以及序列化、 内存拷贝、IPC
            等额外成本；应结合 profiling
            削减可避免的操作，不能将差额全部视为冗余传输。
          

          

            通信瓶颈持续存在，还需要用流水隐藏等待。
            减少通信路径中的额外开销后，端云传输与固定链路时延仍然存在。
            需要让不同请求的计算、传输和 KV
            迁移尽可能重叠，减少通信阻塞计算的时间。
          

          

            大并发下，请求等待是主要开销，需要端云协同调度。
            C16 下，请求在计算步骤之外的等待远大于单步执行时间。
            应协同安排企业前后层、云侧 prefill/decode 与 KV 就绪时机，
            减少排队和相互阻塞，才能将局部加速转化为 SLO 下的吞吐提升。
          

          

            结论来自 C16 Baseline 的历史 trace 分析；RPC 区间包含主机处理，
            云侧处理区间也不等于纯 GPU kernel
            时间。下方性能曲线统一使用开环实测。

开环实测 · Baseline 与优化系统

          

            同一模型、四张 A10、4K 输入 / 79 输出、WAN 每方向 10Gbps / 单向
            5ms。 Baseline 为 TP2+2，优化系统为企业 TP1 + 两个 TP1 P + TP1 D；
            两者服务端 max_active=96、KV
            blocks=32768。相同到达率使用相同泊松请求计划，客户端不限制并发。
          

          

            横轴为实测完成 QPS，不是设定到达率。延迟按测量窗口内到达的请求统计，
            TTFT 从计划到达时刻起算，包含发包延误；TPOT 是每条请求的平均 token
            间隔。 合格要求到达、完成两个 cohort 均有至少 99% 请求同时满足 TTFT
            ≤ 3s、TPOT ≤ 100ms，错误计失败。 每点预热 30s，粗扫测量
            60s、高负载点 120s，再保持到达 30s 后排空。
