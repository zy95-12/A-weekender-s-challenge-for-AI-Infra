# PD chunk 迁移：4K / C16 实测

在 E1/P2/D1 上，独立控制通道＋按 chunk 迁移将首二 token 间隔均值从 **75.8 降到 47.4 ms（−37.4%）**，P99 从 **145.1 降到 63.7 ms（−56.1%）**。QPS 约 3.55，基本持平；TTFT 均值从 509.1 到 521.3 ms（+2.4%）。这次证明的是交接延迟改善，没有证明整体吞吐上升。

## 设置与口径

- Qwen2.5-3B-Instruct，revision `aa8e72537993ba99e69dfaafa59ed015b17504d1`；4×A10、FP16、E-front/cloud/E-back=4/27/5 层。
- 同一 4096-token prompt，生成 79 tokens；Stage1 shm/wire-fast/TCP16MiB，Stage2 chunk1024/decode-first/quota4，Stage3 window2。P/D 独立窗口沿用 PR #16。
- WAN 双向各 10 Gbps、单程 5 ms；P/D 云内 NCCL。性能测量关闭 KV 哈希和 operator profiling。
- C16 闭环，所有客户端至少一次预热，测量至少 60 秒且每客户端至少 6 个稳定周期。下表按完成请求 cohort 统计；起始 cohort 的 SLO 也检查。
- SLO 为每请求 TTFT≤3s 且**请求平均 TPOT≤100ms**，至少 99% 请求达标。全部实验两种 cohort 均 100% 达标；不是每个 token 间隔≤100ms，也没有搜索最大 SLO QPS。
- 原版冻结在 PR #16 的 `edb292d`，每个正式测量前后检查源文件 SHA256 不变。两种新方案都包含实际 forward-stream 完成事件发布及独立控制通道，只在 chunk 开关上不同。

## 性能结果

延迟单位 ms，单元格为均值 / P99。

| 方案 | 正式请求数 | QPS | TTFT | TPOT | 首二 token 间隔 |
|---|---:|---:|---:|---:|---:|
| 原版 E1/P1/D2 | 166 | 2.765 | 2117.9 / 2230.2 | 47.02 / 50.23 | 157.2 / 201.8 |
| 原版 E1/P2/D1 | 214 | 3.554 | 509.1 / 674.6 | 51.18 / 53.47 | 75.8 / 145.1 |
| E1/P2/D1，仅独立控制通道 | 215 | 3.569 | 504.3 / 560.8 | 50.96 / 52.38 | 49.9 / 80.3 |
| E1/P2/D1，控制通道＋chunk | 214 | 3.553 | 521.3 / 650.3 | 50.98 / 52.69 | 47.4 / 63.7 |
| E1/P1/D2，控制通道＋chunk | 163 | 2.716 | 2264.7 / 2377.7 | 46.44 / 48.47 | 57.1 / 114.0 |

原调度的 E1/P1/D2 虽然 TPOT 较低，但 TTFT 和交接等待明显更高。不能把原调度结果外推成 GPU 分配的固有上限，因此也补测了新实现的 E1/P1/D2：首二间隔明显改善（157.2→57.1 ms），但 QPS 仍只有 2.72，TTFT 约 2.26s，未逆转该 C16 场景下 P2/D1 的优势。

## 收益来自哪里

在 P2/D1 的正式请求中：

| 观测 | 原版整段迁移 | 仅独立控制通道 | 控制通道＋chunk |
|---|---:|---:|---:|
| 首 token 计算结束后暴露的 KV 等待，均值 / P99 ms | 19.78 / 86.56 | 0 / 0 | 0 / 0 |
| KV 在首 token 计算结束前 ready 的比例 | 53.3% | 100% | 100% |
| 最终接收线程时长，均值 ms | 33.35 | 11.84 | 5.17 |
| 接收结束→ready，均值 ms | 5.00 | 2.33 | 2.59 |
| 首 token 与 KV 均 ready→首次 decode front，均值 / P99 ms | 11.36 / 35.86 | 7.34 / 24.45 | 5.72 / 14.78 |
| 最终 prefill 响应前已迁移的前缀 | 0 | 0 | 81 MiB |
| 最后一次需迁移的数据 | 108 MiB | 108 MiB | 27 MiB |

原版 start/status/commit 会排在 GPU forward 后，独立通道消除了这部分交接阻塞。chunk 进一步将最后一段接收线程时长降低约 56%，并已实际提前迁移 3/4 KV；总迁移量仍为 108 MiB，没有重复传输前缀。

相对“仅独立通道”，chunk 的首二间隔均值改善约 5.1%、P99 改善约 20.7%，QPS 下降约 0.4%、TTFT 均值上升约 3.4%。两者的暴露 KV 等待已经为零，所以不能把剩余首二间隔差异全部归因为 KV 等待；异步复制还会改变资源竞争和 batch 时序。每组仅一次有界测量，尤其尾百分位不代表统计显著性结论。

原版 / 仅通道 / chunk 的逐请求最大 ITL P99 分别为 261.3 / 146.7 / 159.1 ms，全部 token 合并 ITL P99 为 75.2 / 67.0 / 71.5 ms。首二间隔改善没有消除其他 token 的长尾。

## 正确性与复现

- 62 个 CPU 测试通过，包含控制查询绕过繁忙 GPU 命令锁、范围幂等/连续性、非整页边界、未完成前缀导出拒绝、最终 commit 与取消安全。
- E1/P2/D1 GPU 验证：C16 输出一致；21 个完成迁移请求、78 个范围的每个全局 KV head，源张量与实际 D 页 SHA256 完全一致。覆盖独立 257-token prompt、仅输出 1 token、两种 prefill 取消时点，E/P/D 最后均无残留 KV。
- 对齐绝对位置后，与原版相同 TP 配置比较：4K 的 4095..4102、独立输入的 256..263，共 16 行各 151936 logits **逐元素完全相同**，最大/平均 logit 误差和最大 softmax 概率误差均为 0，16/16 top1 一致。这是两个代表输入的验证范围。
- E1/P1/D2 额外以 chunk=1000 验证非整页中间边界，6 个完成迁移请求、22 个范围哈希完全一致；完整前缀依次为 992、2000、2992、4000、4096，覆盖最后只剩 96 tokens 的迁移。
- 原始请求/逐 token 轨迹、每个 chunk 的时序、配置、源文件哈希、网络验收、NPZ、测试日志和复算脚本打包发布。`pd_chunk_audit.py` 检查所有测量请求（含预热/排空）的绝对位置、首次 decode 不早于 KV-ready、P 释放晚于传输完成、chunk 无缺口/重复及总字节数。
